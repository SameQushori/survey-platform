# Vecta — Product Specification

Статус: продуктовая логика MVP зафиксирована

Дата: 2026-08-29

Владелец продукта: владелец репозитория

## 1. Продукт

Vecta — assessment-first веб-платформа для создания корпоративных тестов, безопасного проведения попыток и анализа результатов. Продукт заменяет legacy Survey Platform и начинает работу с чистой Cloudflare D1 без переноса Firebase-данных.

Основной язык MVP — русский. Архитектура и интерфейс должны допускать последующую локализацию, но переключатель языков в MVP не входит.

## 2. Цели MVP

- Организатор создаёт тест, публикует неизменяемую версию и распространяет её по ссылке, коду или QR.
- Участник проходит тест без постоянной учётной записи.
- Сервер контролирует доступ, сроки, допустимость повторной попытки и итоговую отправку.
- Организатор видит достоверные результаты, аналитику вопросов и CSV-экспорт.
- Участник видит итоговый балл только когда организатор включил эту возможность.
- Административные и организаторские действия защищены server-side авторизацией.

## 3. Не входит в MVP

- Перенос старых Firebase-опросов, пользователей и ответов.
- Текстовые ответы и их ручная/автоматическая проверка.
- Ветвление, матрицы, загрузка файлов и AI-генерация вопросов.
- Частичное начисление баллов за multiple choice.
- Аккаунты участников, социальные функции и публичный каталог тестов.
- Совместное редактирование в реальном времени.
- Нативные мобильные приложения.
- Публичное API и webhooks.

## 4. Роли и границы доступа

### Organizer

- Регистрируется самостоятельно, подтверждая доступ к email одноразовым кодом.
- При первом входе получает собственное личное пространство и активное membership.
- Работает только в организациях, где имеет активное membership.
- Создаёт, редактирует, публикует, закрывает и архивирует тесты своей организации.
- Просматривает попытки, агрегаты и экспорт только своей организации.

### Participant

- Не имеет постоянного аккаунта.
- Получает только публичный DTO теста без answer key, внутренних идентификаторов организации и административных данных.
- Может читать и изменять только собственную незавершённую попытку по короткоживущему подписанному токену.

## 5. Жизненный цикл теста

`draft -> published -> closed -> archived`

- `draft`: редактируемая рабочая версия.
- `published`: создаётся неизменяемый snapshot; начатые попытки всегда привязаны к нему.
- Изменение опубликованного теста создаёт новую версию и не меняет существующие попытки.
- `closed`: новые попытки запрещены, результаты и аналитика сохранены.
- `archived`: тест скрыт из основного списка, но не удаляется.
- Hard delete в MVP отсутствует.

Допустимые обратные действия:

- `closed/archived -> published`: повторный запуск последней публикации; ответы и настройки версии сохраняются.
- `published/closed/archived -> draft`: создание следующей редактируемой версии из immutable snapshot. Активная публикация закрывается для новых попыток, но уже начатые попытки и вся аналитика старой версии сохраняются.
- История результатов остаётся доступна по каждой опубликованной версии.

## 6. Типы вопросов и scoring

### Single choice

- Минимум два варианта.
- Может быть scored или unscored.
- Для scored-вопроса выбирается ровно один правильный вариант.
- Баллы начисляются только за точное совпадение.

### Multiple choice

- Минимум два варианта.
- Может быть scored или unscored.
- Для scored-вопроса выбирается непустой набор правильных вариантов.
- Баллы начисляются только при полном совпадении множеств; частичных баллов в MVP нет.

### Rating scale

- Непрерывная целочисленная шкала с заданными минимумом и максимумом.
- Не участвует в score и используется как аналитический вопрос.

### Общие правила

- Вес scored-вопроса — положительное целое число; значение по умолчанию: `1`.
- Пропущенный scored-вопрос даёт `0` баллов.
- `maxScore` — сумма весов scored-вопросов опубликованной версии.
- Итоговый score вычисляет только Worker по snapshot версии и сохранённым ответам.
- Pass/fail threshold и сертификаты не входят в MVP.

## 7. Режимы участия

### Открытый режим

- Вход по общей ссылке, QR или короткому коду.
- Перед стартом участник вводит отображаемое имя и проходит Turnstile.
- Организатор выбирает: повторные попытки разрешены или действует best-effort ограничение одной попытки на локальную participant identity.
- Открытый режим не обещает строгую уникальность человека. Для строгого ограничения используется контролируемый режим.

### Контролируемый режим

- Для приглашения создаётся криптографически случайная персональная одноразовая ссылка/токен.
- Приглашение разрешает одну завершённую попытку.
- Повторное открытие во время активной попытки восстанавливает её в пределах срока действия.
- После отправки, истечения или отзыва приглашение нельзя использовать для новой попытки.
- Постоянный аккаунт участника не создаётся.

## 8. Попытка

- Worker проверяет публикацию, режим доступа, лимит попыток, Turnstile и rate limit до создания Attempt.
- Время старта и deadline задаёт сервер.
- Клиентский таймер является только отображением server deadline.
- Ответы сохраняются с проверкой типов и принадлежности вопроса snapshot-версии.
- Submit идемпотентен: повтор одного запроса возвращает тот же результат и не создаёт дубликат.
- После успешного submit ответы попытки неизменяемы.
- При истечении времени сервер принимает текущее сохранённое состояние как финальное; несохранённые клиентские изменения не учитываются.

## 9. Результат участника

- `showParticipantResult` по умолчанию равен `false`.
- При `false` после submit показывается только подтверждение завершения.
- При `true` показываются `score` и `maxScore`.
- Правильные варианты, answer key и разбор ошибок участнику в MVP не показываются.
- Независимо от UI answer key отсутствует в participant API response.

## 10. Результаты организатора

- Overview: количество начатых/завершённых попыток, средний score, распределение score и completion rate.
- Question analysis: распределение вариантов, доля правильных ответов для scored-вопросов, пропуски.
- Attempts: отображаемое имя/приглашение, статус, время старта/отправки, duration, score/maxScore.
- Экспорт CSV повторяет разрешённые поля UI и нейтрализует значения, начинающиеся с `=`, `+`, `-` или `@`.
- Доступ всегда ограничен текущей организацией на сервере.

## 11. Ключевые экраны

- Публичная главная.
- Вход/регистрация организатора и ошибки подтверждения email.
- Organizer dashboard, список тестов и состояния empty/loading/error.
- Builder, preview, publish confirmation и distribution.
- Participant entry, instructions, question, navigation, submit confirmation и result.
- Results overview, question analysis, attempts и export.
- Invalid/expired code, closed test, rate limited, offline/network error и 404.
- Desktop и mobile состояния для каждого критического сценария.

## 12. Нефункциональные требования

- TypeScript strict для frontend, Worker и shared domain.
- WCAG 2.2 AA для ключевых сценариев; полная клавиатурная навигация и видимый focus.
- Все mutation endpoints имеют validation, authorization, request ID и идемпотентность там, где возможен повтор.
- Никаких ответов, токенов, паролей и персональных данных в application logs.
- Секреты находятся только в Cloudflare Secrets/CI secrets.
- Production запрещён при падающих lint, typecheck, unit, integration, E2E, build или security checks.

## 13. Auth gate

Production-вход организаторов — встроенный email One-time Code. Vecta не хранит пароли; Worker проверяет непросроченную server-side session cookie и затем роль/membership в D1. Изолированная локальная test identity допустима только на localhost/`.test` и не является production fallback.

## 14. Definition of Done MVP

- Все обязательные сценарии реализованы согласно этому документу.
- Permission matrix и server-side checks покрыты integration/E2E тестами.
- Scoring подтверждён fixture-наборами.
- Участник ни при одном публичном запросе не получает answer key.
- Staging прошёл UAT, security review и accessibility QA.
- Production развёрнут воспроизводимо на Cloudflare и имеет проверенный rollback.
